# Поля Битрикс24 и типы активностей

Конкретные объекты и свойства Битрикс24 (через MCP), а также колонки
CSV-выгрузки CRM, которые читает и в которые пишет навык `crm-maintenance`.
Всё остальное в Битрикс24 или CSV, что не перечислено здесь, навык не трогает.

## Источник 1 — Битрикс24 (MCP)

### Контакты — запись

| Поле | Использование |
|---|---|
| `EMAIL` | Основной идентификатор для поиска и дедупликации. Всегда указывается при создании. |
| `NAME` | Имя — из подписи письма или приглашения календаря, если доступно. Оставить пустым, если неизвестно. |
| `LAST_NAME` | Фамилия — аналогично. |
| `COMPANY_TITLE` / `COMPANY_ID` | Из домена подписи письма или названия организации в календаре, если доступно. |

Больше никакие свойства контакта не пишутся. Ответственный, стадия жизненного
цикла и источник — поля, которыми управляет владелец; никогда не
перезаписывать.

### Контакты — чтение (для поиска)

| Поле | Использование |
|---|---|
| `EMAIL` | Ключ поиска. Сравнение без учёта регистра. |
| `NAME` · `LAST_NAME` · `COMPANY_TITLE` | Показываются владельцу при разрешении неоднозначности. |
| `ID` | Используется для привязки к сделкам и активностям. |

### Сделки — чтение (все сценарии чистки и разрешения)

| Поле | Использование |
|---|---|
| `TITLE` | Показывается владельцу; используется для нечёткого сопоставления с темой письма или встречи |
| `STAGE_ID` | Только чтение при чистке — отмечать расхождения, никогда не менять |
| `OPPORTUNITY`, `CURRENCY_ID` | Читается при чистке; отмечать, если недавнее письмо или встреча предполагают изменение |
| `CLOSEDATE` | Читается при чистке; отмечать, если устарела |
| «Следующий шаг» (кастомное поле сделки, название и код своё у каждого портала, либо комментарий в Таймлайне) | Читается + предлагаются обновления при чистке |
| `ASSIGNED_BY_ID` (ответственный) | Показывается владельцу; никогда не меняется |
| `DATE_MODIFY`, последняя запись в Таймлайне | Используется для выявления зависших сделок |
| `CONTACT_ID` / `COMPANY_ID`, привязанные контакты | Используется, чтобы понять, привязаны ли участники недавних писем или встреч к сделке |

Название полей и стадий у каждого портала своё — не требуйте точного
совпадения, определяйте по смыслу.

### Сделки — запись (только сценарий чистки, с подтверждением)

| Поле | Правило |
|---|---|
| «Следующий шаг» | Предложить обновление; писать только с явным подтверждением владельца |
| `CLOSEDATE` | Предложить обновление; писать только с явным подтверждением владельца |
| `OPPORTUNITY` | Предложить обновление; писать только с явным подтверждением владельца |
| Привязка контакта | Предложить добавление недостающих участников сделки; писать только с подтверждением |

**Никогда не писать** `STAGE_ID`, `CATEGORY_ID` (воронка), `ASSIGNED_BY_ID` или
любое кастомное поле сделки при чистке без прямого запроса владельца на
конкретное изменение. Это поля, которыми управляет владелец.

### Активности — запись (Таймлайн сделки)

| Тип активности | Кто использует | Заполняемые поля |
|---|---|---|
| Письмо | Сценарий «письмо» | Тема (тема цепочки), содержание (резюме, не полная цепочка), время (по последнему сообщению), привязанный(е) контакт(ы) + сделка |
| Звонок | Сценарий «звонок» | Тема (название события), содержание (резюме), длительность (из календаря), время (начало события), привязанный(е) контакт(ы) + сделка |
| Комментарий в Таймлайне | Сценарий «чистка» | Текст комментария — когда что-то отмечается для будущей проверки, но не подходит под обновление конкретного поля |

Используйте стандартные типы активностей Битрикс24 (звонок, письмо, встреча).
Не изобретайте собственные типы. Конкретные технические коды типа активности
различаются между версиями портала — ориентируйтесь на человекочитаемое
название, а не на номер кода.

### Правила привязки

- Каждая активность должна быть привязана к сделке И минимум к одному контакту.
- Если контакт создаётся «на лету» при логировании активности, привязывайте
  его к сделке той же операцией — чтобы активность появилась в Таймлайне и
  контакта, и сделки.
- Не привязывайте контакт к сделке в рамках логирования активности, если он
  не является реальным участником этого письма или встречи.

## Источник 2 — CSV-выгрузка CRM (fallback), `crm_клиенты.csv`

Если Битрикс24 (MCP) не подключён, используйте ту же выгрузку CRM, что и
навык `lead-triage`.

| Колонка CSV | Соответствует полю Битрикс24 | Использование |
|---|---|---|
| `имя` | `TITLE` / имя контакта | Отображение |
| `контакт` | `EMAIL` / `PHONE` | Получатель / участник |
| `стадия` | `STAGE_ID` | Чтение при чистке — отмечать расхождения |
| `предложение` | — | Контекст сделки |
| `сумма`, `валюта` | `OPPORTUNITY`, `CURRENCY_ID` | Читается при чистке |
| `последний_контакт` | `DATE_MODIFY` / последняя запись в Таймлайне | Выявление зависших сделок |
| `следующий_шаг` | «Следующий шаг» | Читается + предлагаются обновления |
| `заметки` | Комментарий в Таймлайне | Контекст, доказательства для чистки |

Для CSV-выгрузки запись означает добавление новой строки или обновление
ячейки в файле — только после подтверждения владельца, так же как запись в
Битрикс24. Самописная CRM может называть колонки иначе — сопоставляйте по
смыслу (имя/сумма/дата/стадия), точную схему не требуйте. Если файла нет
вовсе — отметьте «н/д — нет выгрузки CRM» и не выдумывайте сделки.
