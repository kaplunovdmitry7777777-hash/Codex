Правила основного файла навыка имеют приоритет над примерами. Если пример предполагает конкретный путь, версию библиотеки или приложение, проверь доступный аналог.

# Метод Семёна Мошкина

Скилл для работы с большими массивами текстовых документов. Отвечает за три вещи: аккуратный приём файлов (аудит и опциональная конвертация в чистый markdown), упорядоченное чтение (через маппинг от пользователя или собственный индекс), и честную верификацию того, что реально загрузилось в контекст (таблица с маркерами, без самообмана в процентах).

Скилл рассчитан на сценарии, где точность обработки важнее скорости: договорные пакеты, юридический корпус, результаты due diligence, регламенты и приложения к ним.

## Обзор этапов

1. **Аудит** — перечисление форматов, уточнение про конвертацию.
2. **Маппинг** — определение порядка чтения.
3. **Работа с документами** — чтение напрямую или через markdown.
4. **Верификация** — таблица с маркерами по запросу пользователя.

Этапы 1–2 выполняются один раз в начале сессии, этап 3 — это основная работа, этап 4 — по явному запросу.

## Этап 1: Аудит загруженных файлов

Когда пользователь загружает файлы в начале сессии и ставит задачу по ним, первое сообщение скилла — короткий аудит. Формат:

> Загружены файлы: N штук — [перечень форматов].
> [Короткая рекомендация по конвертации, если применимо].
> [Вопрос по порядку чтения, если применимо].
> Готов приступить к задаче.

### 1.1 Классификация файлов

Пройдись по списку и отнеси каждый файл к одной из категорий:

- **`.md`** — уже в оптимальном формате, ничего не требуется
- **`.docx`** — чистый текстовый источник, конвертация выгодна
- **`.txt`** — текст, может потребовать проверки кодировки
- **`.pdf` (с текст-слоем)** — чистый источник, конвертация выгодна
- **`.pdf` (скан без текст-слоя)** — требует OCR, долго и с потерями
- **`.jpg`, `.png`, `.webp`** — скан-изображения, требуют OCR

Если не можешь определить тип PDF (с текст-слоем или скан) без чтения — отметь его как «PDF, тип уточним при чтении».

### 1.2 Решение о необходимости конвертации

Используй следующие правила:

| Ситуация | Действие |
|---|---|
| Все файлы уже в `.md` | Конвертация не нужна, сразу к этапу 2 |
| 1–2 небольших файла (каждый ≤50 КБ), задача простая | Читай напрямую, про конвертер не упоминай |
| 3+ файлов ИЛИ любой файл >50 КБ | Предложи конвертер (см. 1.3) |
| Есть PDF-сканы | Дополнительно предупреди о времени OCR (15–25 минут на 50-страничный скан) |
| Есть DOCX и PDF-скан одного документа | Рекомендуй работать с DOCX как основным источником (скан — только для проверки подписей/печатей) |

«Размер файла» тут — это не точный критерий, а индикатор. Если файлы пограничные (30–60 КБ), ориентируйся на их содержимое и задачу: для простого вопроса — напрямую, для глубокого анализа — через конвертацию.

### 1.3 Отдача конвертера пользователю

Если решено предлагать конвертацию, **отдай standalone-конвертер через тул `present_files`** из `assets/md-converter-standalone.html`. Формулировка:

> Для экономии контекста и более точной работы рекомендую сначала сконвертировать документы в `.md` локально. Инструмент приложил: откройте HTML в браузере, перетащите файлы, получите `.md` и загрузите их обратно в чат. Работает офлайн, ничего не отправляется на сервер.
>
> Или напишите «конвертируй» — сделаю сам. Или «работай как есть» — начну с исходными форматами.

Три варианта действий пользователя, все валидны:

- **«конвертируй»** → скилл конвертирует сам: создаёт по одному `.md` на каждый исходник в `<approved-output-directory>/`, используя `mammoth` для DOCX, `pdfplumber`/`pdf2image`+`pytesseract` для PDF, автодетекцию кодировки для TXT. Медленнее и тратит контекст, но иногда удобнее для пользователя.
- **«работай как есть»** → переходим к этапу 2, читаем исходные форматы напрямую.
- **Пользователь возвращается с `.md` файлами** → отлично, работаем с ними.

### 1.4 Подтверждение факта конвертации

Если пользователь загружает **только .md** файлы с самого начала — не спрашивай про конвертацию, это уже сделано. Сразу переходи к этапу 2.

Если загружены **смешанные** форматы (часть уже .md, часть исходные) — явно раздели:

> По `.md` файлам работаю сразу. По остальным ([перечислить]) — что делать: конвертировать, или читать напрямую?

## Этап 2: Маппинг и порядок чтения

Порядок обработки документов — часть контекста. Один и тот же набор файлов, прочитанный в разных последовательностях, даёт разное понимание. Например, акт приёмки после договора — это подтверждение исполнения; акт без договора — просто перечень работ. Скилл **обязательно** уточняет порядок до начала серьёзной работы.

### 2.1 Четыре сценария навигации

Реагируй на них в таком приоритете:

**(A) Явный порядковый маппинг от пользователя в тексте.**
Фразы: «сначала прочитай X, потом Y, затем Z», «читай в порядке: A → B → C», «начни с договора, закончи приложением 4».
→ Запомни порядок как упорядоченный список, строго следуй ему. В таблице верификации (этап 4) файлы идут в том же порядке.

**(B) Отдельный индексный файл от пользователя.**
В загрузке есть файл типа `index.md`, `оглавление.md`, `00_mapping.md`, `ПРОЧТИ_ПЕРВЫМ.md`.
→ Открывай его первым, читай как инструкцию по порядку, дальше следуй указаниям из него.

**(C) Осмысленная нумерация в именах файлов.**
Например: `01_договор.pdf`, `02_допник.pdf`, `03_акт.pdf`, или `часть_1.docx`, `часть_2.docx`, или даты в именах (`2024-03-01_отчёт.pdf`).
→ Предложи этот порядок явно и попроси подтверждения: «Вижу нумерацию в именах — читаю в порядке 01 → 02 → 03. Подтвердите или задайте свой порядок».

**(D) Ничего из вышеперечисленного.**
→ Действуй по количеству файлов:
- **Файлов мало (≤4)** — читай в порядке загрузки, честно сообщи: «Порядок произвольный, если важна последовательность — скажите».
- **Файлов много (5+)** — предложи собрать индексный файл:
  > Документов много, порядок не очевиден. Хотите, я сначала пробегусь по файлам, соберу индексный файл с краткими аннотациями по каждому и предложенным порядком чтения? Вы его посмотрите, поправите, и дальше я буду работать строго по нему.
  >
  > Или работать без индекса — скажите «работай так».

### 2.2 Сбор индексного файла

Если пользователь согласился на формирование индекса:

1. Быстро прочитай каждый файл (достаточно первых 2–3 страниц каждого).
2. Для каждого сформулируй 1 предложение о сути.
3. Определи смысловые связи (ссылки, приложения, последовательность).
4. Предложи порядок чтения исходя из логики документов.
5. Сохрани результат в `index.md` через `create_file`.
6. Отдай пользователю через `present_files`.
7. Жди подтверждения или правок перед дальнейшей работой.

Пример структуры индекса:

```markdown
# Индекс корпуса документов

## Предлагаемый порядок чтения

1. договор_2024.pdf — базовый договор
2. допник_1_от_15.03.2024.pdf — изменение по срокам
3. допник_2_от_10.09.2024.pdf — изменение по сумме
4. акт_Q3_2024.pdf — исполнение за 3 квартал
5. акт_Q4_2024.pdf — исполнение за 4 квартал

## Аннотации

- **договор_2024.pdf** — Основной договор между А и Б на поставку. Сумма 10 млн, срок 12 мес.
- **допник_1_от_15.03.2024.pdf** — Продление срока на 3 мес.
- …
```

## Этап 3: Правила работы с документами

### 3.1 Прямое чтение исходных форматов

Если задача поставлена сразу и пользователь не просил конвертацию, читай исходные форматы без предварительного преобразования:

- `.md`, `.txt` — напрямую из контекста или через `view`
- `.docx`, `.pdf` — по протоколу соответствующих скиллов (`docx`, `pdf-reading`), которые умеют доставать текст эффективно
- Картинки со сканом — через `view` (увидишь изображение) или через OCR, если нужен текст для поиска

Не конвертируй молча. Если для ответа действительно нужна конвертация — сообщи и спроси.

### 3.2 Иерархия форматов по качеству

Когда у пользователя есть выбор (например, договор и в DOCX, и в PDF-скане), применяй такой приоритет:

1. **DOCX оригинал** — идеальный источник, структура сохранена.
2. **Текстовый PDF (с текст-слоем)** — хорошо, структура частично теряется.
3. **TXT** — хорошо для плоского текста, но надо следить за кодировкой.
4. **JPEG/PNG-скан одной страницы через OCR** — приемлемо для понимания сути.
5. **Многостраничный PDF-скан через OCR** — наименее надёжный, с потерями.

Если у пользователя есть одновременно, скажем, DOCX-версия договора и его подписанный PDF-скан — предложи работать с DOCX по содержанию, а скан использовать только для проверки факта подписания (наличие печатей, подписей).

### 3.3 Предупреждения про OCR

OCR — это компромисс. Когда используешь результаты OCR, явно предупреждай пользователя о типичных проблемах:

- **Кириллица ↔ латиница путается.** Буквы А, В, Е, К, М, Н, О, Р, С, Т, Х, У визуально похожи на латинские и распознаются то так, то так. При поиске по документу учитывай оба варианта или нормализуй текст.
- **Номера пунктов в боковых колонках теряются.** В договорах нумерация «1.1., 1.2., 1.3.» часто оформлена вне основной колонки мелким шрифтом — OCR ловит их частично.
- **Логотипы и печати дают мусор.** Графические элементы распознаются как случайные символы.
- **Время обработки.** 54-страничный PDF-скан через OCR в браузере — 15–25 минут. Предупреди об этом до начала прогона.

Когда цитируешь OCR-результат в юридически значимом контексте (точная сумма, конкретный пункт, реквизиты) — явно помечай: «Данные из OCR-результата, рекомендую сверить с оригиналом».

### 3.4 Ссылки на файлы

При ответах **всегда ссылайся на конкретное имя файла** из маппинга. Не «в одном из документов», а «в `договор_2024.pdf`». Если порядок чтения задан — можно дополнительно указывать позицию: «в третьем документе по маппингу — `акт_Q3_2024.pdf`».

## Этап 4: Верификация контекста

Когда пользователь явно просит проверить загруженные файлы — «составь таблицу по файлам», «что ты изучил», «проверь, что всё загрузилось», «покажи, что прочитал» — скилл строит верификационную таблицу.

### 4.1 Формат таблицы

| Имя файла | Статус загрузки | Ключевые маркеры | Краткое содержание |
|---|---|---|---|
| `договор_2024.pdf` | Прочитан | «ООО Альфа», «10 000 000 ₽», «31.12.2024», п. 4.2.3, ст. 421 ГК | Основной договор поставки между А и Б, сумма, сроки, форс-мажор |
| `акт_Q3_2024.pdf` | Прочитан | «25.09.2024», «акт № 47», «2 500 000 ₽», подпись Петров | Приёмка работ за 3 квартал, сумма, ссылка на договор |
| `скан_печати.jpg` | Частично прочитан (OCR) | «ПЕЧАТЬ АО АЛЬФА», ИНН 7701234567 | Оттиск печати, реквизиты юрлица |

Порядок строк в таблице соответствует **порядку чтения** из этапа 2, не порядку загрузки.

### 4.2 Три статуса

- **«Прочитан»** — содержимое в контексте, ключевые факты и структура понятны.
- **«Частично прочитан»** — для больших файлов, где в контекст попала часть (например, при сокращённом чтении PDF). Или для OCR-результатов с известными потерями (скан, картинки, сложные сканы).
- **«Не читал»** — файл был загружен, но до него не дошло (например, пользователь загрузил 20 файлов, а задача касалась только первых 5).

Не используй проценты. «Изучено на 87%» — это самообман, у тебя нет способа объективно измерить полноту. Статус — это твоя честная оценка из трёх категорий.

### 4.3 Ключевые маркеры

Маркеры — это **конкретные, специфические** данные из файла, которые доказывают, что ты его действительно прочитал. Хорошие маркеры:

- Числа (суммы, даты, номера, проценты)
- Имена (людей, организаций)
- Уникальные термины (названия проектов, реквизиты, номера пунктов)
- Точные ссылки на статьи/законы

Плохие маркеры — общие фразы типа «договор содержит обязательства сторон» (подходит к любому договору).

По 3–5 маркеров на файл.

### 4.4 Честное признание неполноты

Если ты не уверен, что файл прочитан полностью (был большой, или OCR дал потери, или в контекст попала только часть) — **говори об этом прямо**. Например:

> Файл `большой_регламент.pdf` — 120 страниц, прочитал первые 40 и последние 10. Серединные разделы (главы 4–8) не в контексте. Если нужна проверка по ним — уточните, перечитаю.

Пользователь должен понимать реальную картину. Лучше признать ограничение, чем сделать вид, что всё под контролем, а потом выдать галлюцинацию.

## Приложения

### Конвертер `md-converter-standalone.html`

Standalone HTML-инструмент в `assets/`, который пользователь открывает в своём браузере. Работает офлайн, после первой загрузки библиотек с CDN. Поддерживает:

- **DOCX** → markdown (через mammoth.js)
- **TXT** → markdown с автодетекцией кодировки (UTF-8 → Windows-1251)
- **PDF** с текст-слоем → извлечение текста (через pdf.js)
- **PDF-скан** → OCR (через tesseract.js), автоматически в режиме «Авто»
- **JPG / PNG / WebP** → OCR

Дефолтный режим для PDF — «Авто»: сначала пробует извлечь текст, если его мало (<50 символов на страницу в среднем) — автоматически переключается на OCR. Пользователю обычно ничего не нужно настраивать.

**Когда отдавать пользователю:** см. этап 1.3.

**Когда конвертировать самому (если пользователь просит «конвертируй»):** используй python-библиотеки в своей песочнице:
- DOCX: `mammoth.convert_to_html` + кастомный `html_to_markdown` (логика та же, что в HTML)
- PDF-текст: `pdfplumber` или `pypdf`
- PDF-скан: `pdf2image` + `pytesseract` с `lang='rus+eng'`
- TXT: `read_bytes()` + декодирование с фолбэком на cp1251

Но учти, что самостоятельная конвертация тратит твой контекст и занимает время. Отдавай HTML, когда файлов много.

### Типичные формулировки пользователя и реакция

- *«Загрузил документы, изучи»* → аудит (1.1-1.2) + вопрос про маппинг (2.1)
- *«Составь таблицу по файлам»* → этап 4 (верификация)
- *«Что ты прочитал?»* → этап 4 (верификация, кратко)
- *«Сначала X, потом Y»* → сценарий A этапа 2
- *«Сделай сводку»* / *«Подытожь»* → если есть маппинг — идёт по нему, если нет — уточнить
- *«Конвертируй»* → обработай сам через python-библиотеки, отдай `.md` через `present_files`
- *«Работай как есть»* → переходи к этапу 2, без конвертации

### Что скилл НЕ делает

- Не редактирует документы (для этого `legal-doc-editor` и `docx`).
- Не реструктурирует документооборот (для этого `doc-workflow-audit`).
- Не даёт юридических заключений и не оценивает риски по документам — только работает с фактическим содержимым.
- Не «придумывает процент изучения».
